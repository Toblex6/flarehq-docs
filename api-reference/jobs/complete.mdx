Mainnet completion is unavailable without an externally verified protocol address. **No mainnet job payout was performed.** Authentication can run before the handler's `503 erc8183_unavailable` guard.

## Request and authority

`POST /api/jobs/complete` accepts an active internal key, active verified merchant API key, supported merchant session or database-bound consumer session. Required: `jobId` and `evaluatorWalletId`. Optional `reason` defaults to `deliverable-approved`.

The Circle wallet must resolve to the stored job evaluator. The server checks `verifyCallerControlsAddress` and applicable consumer step-up. If the job requires validation, the release gate must be satisfied or the route returns `409 VALIDATION_REQUIRED` before completion.

The **evaluator** must review the work and authorize the decision. The API does not itself establish that the deliverable meets the requirements. It hashes the reason and calls `complete(uint256,bytes32,bytes)` on the configured protocol. Passing the client wallet is insufficient unless that wallet is the designated evaluator.

## Response and consequences

Fresh success includes `success`, `jobId`, `status: 'COMPLETED'` and `txHash`. The protocol completion is intended to release its job escrow to the provider; this is not checkout or a criterion-stream close action.

The handler updates the stored job after chain completion, then attempts ledger entries, eligible auto-reputation and Telegram human-provider notification. Those secondary effects are caught/best-effort; success does **not** prove every ledger/feedback/notification write completed. Verify recipient credit and any fees independently.

No client idempotency key or fully atomic chain/database lifecycle exists here. A receipt can have succeeded before an HTTP/database failure. Inspect the original receipt, contract state, actual provider credit, stored job and explorer before another action. Never infer a refund or repeat payout from a timeout.

Missing fields/malformed job ID/wallet return `400`; absent job `404`; evaluator/control mismatch `403`; validation requirement `409`; caught execution/persistence error `500`. Protocol state/expiry rules apply; no separate reject/refund action is implemented by this endpoint.
