## GET /api/jobs/list

Requires an active verified merchant's API key or supported merchant session. Rows are scoped to its `merchantId`, newest first. Optional `status`, `clientAddress` and `providerAddress` add exact stored-value filters. No pagination or date filters are implemented.

Returns `success`, `jobs` and `count`. Each row has database `id`, protocol `jobId` string, client/provider SCAs, description, `budget` string, stored status and creation time. `budget` is **6-decimal USDC base units**, not a human amount.

This route performs no chain read or mainnet availability guard. Historical stored rows can remain visible without an executable mainnet protocol, and this list does not apply a separate network filter. A listing is not proof of funding, live status or a completed payout.

Missing authentication returns `401`; caught database/filter errors `500`.

## GET /api/jobs?jobId={jobId}

Accepts an active internal key, active verified merchant API key, supported merchant session or database-bound consumer session. The wrapper authenticates first; unconfigured mainnet ERC-8183 then returns `503 erc8183_unavailable`. Missing/malformed job ID returns `400`; caught RPC/decode failure `500`.

With a configured protocol it reads `getJob` and returns `success`, `job`, `contractAddress` and explorer address URL. `job` includes ID, title-case status, numeric status code, human-readable `budgetUSDC`, parties, description, expiry, hook and `isExpired`.

It adds `isProvider`, `isClient` and `budgetZero` for the Manage UI from the caller's controlled-address set. These flags are **read hints**, not authorization. Lifecycle routes still enforce role/ownership checks. The authenticated read is not scoped to the caller's own job ID.

`isExpired` is a time comparison; it does not force a status-code transition. A deadline can pass while a stored/contract status remains OPEN. Do not claim merely reading the deadline refunds or changes a job.
