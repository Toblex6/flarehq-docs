Mainnet ERC-8183 execution is unavailable without a verified protocol address. No mainnet deliverable was submitted here. The outer key/session wrapper can return `401` before the handler's `503 erc8183_unavailable` guard.

## Request

`POST /api/jobs/submit` accepts an active internal key, active verified merchant API key, supported merchant session or database-bound consumer session. Send:

| Field | Requirement |
|---|---|
| `jobId` | Protocol job ID, not agent Registry ID/token ID. |
| `providerWalletId` | Circle wallet UUID that must resolve to the job's stored provider SCA. |
| `deliverableData` | Non-empty work-output string, such as an actual HTTPS/IPFS URI. |

The server checks provider membership and `verifyCallerControlsAddress`, then applies consumer step-up where required. It hashes the UTF-8 string with keccak256 and submits `submit(uint256,bytes32,bytes)`.

The handler does **not** fetch the output, validate a URI scheme, evaluate quality or store the full deliverable string. A hash alone is not successful work. Preserve the actual output and any required availability evidence for the evaluator.

## Response and replay

Fresh success includes `success`, `jobId`, `status: 'SUBMITTED'`, `deliverableHash` and `txHash`. The stored row receives the hash/status/history after the transaction. Job state/expiry rules are enforced by the protocol, not a promise every invalid state is caught before spending gas.

No client idempotency key or atomic chain/database write is implemented here. A timed-out or failed database update can follow a successful transaction. Inspect the original receipt and job state before resubmission; do not turn an ambiguous response into another chain action automatically.

Missing fields/malformed job ID/wallet return `400`; absent job `404`; provider/control mismatch `403`; caught execution/persistence failure `500`. Completion is a separate evaluator-authorized step, not a consequence of anchoring a hash.
