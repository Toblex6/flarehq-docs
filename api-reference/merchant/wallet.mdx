Both verbs use the active verified merchant's `x-api-key` or supported `merchant_token` session. Invalid supplied keys do not fall back to a cookie.

## GET /api/merchant/wallet

Returns `success` and `wallet` with `walletProvider`, nullable `walletAddress`, nullable `circleWalletId` and `walletVerified`.

On mainnet, a Circle wallet with a bound ID is checked against the configured Circle environment before its deposit address is shown. Stale/wrong-network results return `409` with `WALLET_NEEDS_UPDATE`; transient check failure returns `503` with `WALLET_CHECK_FAILED`. Retry or re-authenticate according to the message. Do not fund a withheld or outdated address. A generic profile field or `walletVerified: false` is not a verified deposit target.

```javascript
// Same-origin browser read; requires the existing merchant session.
const response = await fetch('/api/merchant/wallet', { credentials: 'include' });
const result = await response.json();
if (!response.ok || result.success !== true) throw new Error('Wallet read failed');
```

## PATCH /api/merchant/wallet

Send `{ "walletProvider": "CIRCLE" }`. Any other provider is rejected with `400`; use [the signed connect flow](./wallet-connect.mdx) for an external wallet. Already-Circle accounts with an address receive `409`.

The route applies the withdrawal limiter, provisions a **brand-new** Circle wallet and updates the merchant's wallet binding. It does not restore a previously linked Circle wallet or automatically move its funds. Success returns `success`, `message` and `wallet` with provider/address.

Review future routing before changing wallets. Existing invoice recipient fields stay frozen.
