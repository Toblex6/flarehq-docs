`GET /api/payments/stream` remains an **API-key-authenticated**, read-only database view. It is not evidence that retired create/stop/withdraw operations are available or that mainnet job streams work.

## Query parameters

The route accepts `sender`, `receiver`, `status` and `reference` filters. It returns `success`, `metrics` and `streams`. The audited handler does not scope the underlying query to the authenticated merchant; do not describe this as an owner-isolated history API.

Each stream includes stored fields plus `currentStreamed`, `remainingBalance`, `secondsRemaining`, `percentComplete` and an explorer link when a stored hash exists. These are **local elapsed-time estimates from legacy records**, not live contract reads or verified receiver credit.

The aggregate metrics include record counts, `totalLockedUSDC` and `totalRatePerSecond`. Their labels do not establish actual locked funds on-chain.

## Separate create-path GET

`GET /api/payments/stream/create` is another API-key-authenticated legacy record view. It accepts sender/receiver/status filters and returns `metrics.totalStreaming`; it does not create a stream.

As of November 16, 2026, the readiness run did not authenticate these production views or reconcile their rows with on-chain evidence. [Legacy mutations are retired](/payments/streaming-payments); criterion-based job streams are a different workflow.
