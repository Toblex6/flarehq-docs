## GET /api/escrow/status?reference={reference}

Requires an **active internal service API key**, not the merchant's own key or merchant/consumer session. GET does not bypass this gate. Use a server-side `x-api-key` header; do not put secrets into query URLs, browser code or logs even though the legacy middleware has a query-key path.

The handler looks up one Escrow row by reference. It is **not merchant-owner scoped** and does not read the contract or enforce a network availability gate. Missing key returns `401`; invalid/inactive key `403`; missing reference `400`; no row `404`; caught failures `500`.

Returns `success` and `escrow`, spreading the stored row and adding `isExpired`, `timeRemaining` seconds and an explorer URL for the stored creation hash. These are database/time-derived fields, not live locked-balance or mined-settlement evidence. The current network's explorer base may not be appropriate for every historical row; verify chain identity before following a hash.

Passing the deadline does not refund, release or change stored status. A disputed record cannot be refunded merely because `isExpired` is true. Do not use a cached status as an exact accounting or payout proof.

## GET /api/escrow/list

The merchant-facing stored list instead requires an active verified merchant API key or supported merchant session. Normal rows are scoped by `merchantId`; optional `status`, `depositor` and `beneficiary` filter the returned rows. Metrics cover all that merchant's stored rows before those filters.

`role=beneficiary` selects incoming escrows whose beneficiary wallet is in the caller's controlled-address set, regardless of creating merchant. It uses that role scope rather than the normal field filters. The consumer session alone is not accepted by this merchant list.

Returns `success`, `metrics` and `escrows`, with confirmation links and derived expiry fields. `totalLocked` includes ACTIVE **and DISPUTED** rows. These are stored floating-point sums without a live contract/network reconciliation, not independently verified reserves. No pagination is implemented.

## Mainnet boundary

Create/release/dispute are unavailable pending owner deployment and verification. A readable historical record does not activate those actions. No mainnet escrow was funded or settled in this readiness run.
