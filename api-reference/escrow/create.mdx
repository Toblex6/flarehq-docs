Mainnet escrow creation is **unavailable pending deployment and verification**. Missing configuration returns `503 escrow_unavailable`; invalid configuration returns `503 escrow_misconfigured`. Read [escrow availability](/payments/escrow-and-disputes).

The create network guard runs **before authentication**. Missing/invalid mainnet address returns `503 escrow_unavailable` or `escrow_misconfigured`, with no approval or creation attempt. Never supply a testnet address to mainnet configuration.

## Configured POST /api/escrow/create

Requires an active verified merchant's API key or supported merchant session. The depositor must pass `verifyCallerControlsAddress` as that merchant's controlled wallet. External-wallet creation is unsupported (`501`); this route expects Circle server-authorized execution.

| Field | Behavior |
|---|---|
| `depositorSCA` | Required valid EVM wallet controlled by the authenticated merchant. |
| `depositorWalletId` | Required legacy Circle UUID field. The current handler checks presence but signs by the authorized address; this field is **not** independent signing authority or a live UUID/address proof. |
| `beneficiarySCA` | Required valid recipient address, distinct from the depositor. Not necessarily the creating merchant or a Circle SCA. |
| `amount` | Positive USDC decimal, up to 6 places and at most 10,000,000. |
| `deadlineHours` | Default 24; strictly positive and at most 720. Expiry is not automatic payout. |
| `condition` | Optional text; on-chain default is `No condition set`, while omitted database condition is null. |
| `webhookUrl` | Optional best-effort notification input, not a signed delivery guarantee. |

The server generates the reference and bytes32 on-chain ID, approves USDC, then submits escrow creation. The named contract holds the deposit; **checkout's “FlareHQ never holds funds” description does not mean escrow has no contract custody**.

Creation classifies the beneficiary as merchant, consumer, agent or external before persisting the row and attempts notification. Success includes `success`, `escrow`, creation hash/explorer URL, contract address, beneficiary kind/confirmation URL and next-step templates.

## Deadlines and uncertainty

Two confirmations release to the beneficiary. Either party can dispute before expiry; a disputed escrow requires administrator resolution. An undisputed expired escrow can be refunded by the depositor. Nothing is transferred merely because a deadline passed or a confirmation URL was opened.

Approval, creation, persistence and notifications are **not atomic**. There is no client idempotency key. Reconcile the original Circle operation, receipt, contract balances/state and row before retrying a timeout; a `500` after creation does not undo a deposit.

The locally tested contract rejects inexact deposits and payouts. Mainnet token/fee behavior must be reverified; testnet fee assumptions are not a deployment guarantee. Safe administration and production configuration remain owner-only.
