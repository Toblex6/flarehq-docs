Mainnet escrow is **unavailable pending owner deployment and verification**. The network guard returns `503 escrow_unavailable`/`escrow_misconfigured` before body/authentication/chain operations.

## Configured request

Send `reference` and `callerSCA` to `POST /api/escrow/release`. The stored row must be ACTIVE with a contract ID; the caller address must be its depositor or beneficiary. The server requires `verifyCallerControlsAddress` under the applicable merchant key/session, consumer session or explicitly bound internal-agent identity. Applicable consumer `consumer.escrow-act` step-up remains required.

A merchant key is not control of the other party's wallet. An arbitrary address, full API key or a successful read does not authorize release.

## Execution and response

- Circle-bound parties use server-authorized `confirmDelivery` execution.
- External **merchant** wallets receive `pendingSignature: true`, a queued request ID and transaction payload. Their wallet must broadcast; queue success is **not confirmation or payout**.
- Non-merchant branches still use Circle execution; do not assume this route implements a general external-consumer signature/resume flow. An external beneficiary has a separate evidence-recording endpoint after its own on-chain confirmation.

After Circle execution the server reads `getEscrow` and mirrors both confirmation flags. A one-sided confirmation stays ACTIVE; both flags produce RELEASED. Failed state read returns `500` without advancing stored flags, even when the transaction may already have landed.

Confirmed success includes `success`, updated `escrow`, `txHash`, `explorerUrl` and `released`. Require `released: true` and reconcile actual beneficiary credit before a payout claim. Secondary ledger/webhook effects are best-effort. No client idempotency key or complete chain/database atomicity is implemented.

## External beneficiary evidence

`POST /api/escrow/{reference}/beneficiary-confirm` is a separate public, rate-limited recording path with `callerSCA` and actual mined `txHash`. It checks the transaction's sender, destination, selector, decoded escrow ID, successful receipt and authoritative confirmation state. It **does not sign or move funds itself**; the beneficiary's own wallet transaction does.

The locally tested contract prevents normal confirmation on disputed/expired/settled records. Dispute resolution is administrator-only and cannot be bypassed by this release API. Safe decisions require Safe authorization, not the server's EOA key.
