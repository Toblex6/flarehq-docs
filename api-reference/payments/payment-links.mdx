`POST` and `GET https://flarehq.xyz/api/merchant/payment-link` accept an active verified merchant's **API key or `merchant_token` session**. An internal service key alone is not a merchant identity here. Keep keys server-side and let the browser manage its HTTP-only cookie.

Links are frozen **single invoices with a 24-hour expiry**, not permanent multi-use products. The server freezes the authenticated merchant's name, ID, wallet and USDC token into a PENDING PaymentLog row. Creating a link transfers nothing.

**The customer pays directly to the merchant wallet; FlareHQ never holds checkout funds.** Authenticated merchant-session creation passed on November 19 for a 0.01-USDC link. Public GET and read-only Neon confirmed the bound merchant recipient and unpaid state. Hosted/embed rendering passed. One exact checkout is approved but paused for browser attachment and a different unpaid replay target; no new payment/replay was performed. See [availability](/payments/availability).

## POST fields

| Field | Behavior |
|---|---|
| `amount` | Required positive decimal, maximum 6 decimals and 10,000,000. Prefer a string. |
| `currency` | Accepted input is ignored: new links always use server-resolved USDC. |
| `description` | Echoed in the response or null; **not persisted on the invoice** by this handler. |
| `webhookUrl` | Optional stored notification destination; not a signed delivery or retry guarantee. |

The payout wallet must already be configured. There is no product `name`/`price`, recipient override, activation switch, shipping-address collection or reusable-link API.

```javascript
const response = await fetch('https://flarehq.xyz/api/merchant/payment-link', {
  method: 'POST',
  headers: {
    'x-api-key': process.env.FLAREHQ_API_KEY,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ amount: '0.10', currency: 'USDC' }),
});
const link = await response.json();
if (!response.ok || link.success !== true) throw new Error('Link creation failed');
// Save link.reference; share link.checkoutUrl.
```

This illustrative backend request was not executed with an authenticated production account. POST success includes `reference`, `checkoutUrl`, numeric `amount`, `currency`, canonical `token`, echoed `description`, `merchant` and `expiresIn: '24 hours'`.

## GET view

GET uses the same merchant resolver and returns `{ success: true, links }`. It first queries the newest **100 rows belonging to `merchantId`**, then filters for the selected network. It is not a separate reusable-product table and has no pagination parameters.

Each entry includes:

- `reference`, numeric `amount`, `currency`, canonical `token` and `checkoutUrl`.
- `rawStatus` from storage; `status`/`displayStatus` derived for the view.
- `isExpired`, stored `expiresAt` and creation `createdAt`.

For a past-deadline raw PENDING row, `status`/`displayStatus` is `EXPIRED` while `rawStatus` can remain `PENDING`. GET does not update the row or reconcile live receipts.

## Errors and settlement

`401` means the merchant did not resolve; `400` covers invalid amount or missing payout wallet; `404` covers a missing merchant record. POST uses the shared payments limiter. Inspect the actual body for server/token failures.

Use `/checkout/{reference}` or `/checkout/embed/{reference}`. Before fulfillment, read the [cached verification view](/api-reference/payments/verify), compare your own frozen order and actual transaction evidence, and fulfill once. Top-level `status: true` is not payment success.

Do not retry creation or replace an expired link until you have checked any in-flight payment. [Webhooks are unsigned/best-effort](/developers/webhooks), and `description` is not a reliable persisted order identifier.
