## Authentication

Both verbs accept an active internal service key, active verified merchant API key, supported merchant session or database-bound consumer session. **GET is not public.** A supplied invalid key returns `401`; authentication does not grant control of any named wallet.

Registry address and Circle blockchain resolve from central network configuration. No mainnet validation request/response was submitted in this readiness run.

## POST action: request

Required JSON fields: `action: 'request'`, `agentId` (ERC-8004 **token ID**), `ownerSCA`, `validatorSCA` and `requestTag`.

The stored agent must exist, `ownerSCA` must equal its SCA and `verifyCallerControlsAddress` must authorize that owner. The server derives `requestURI` and a time-dependent `requestHash`, submits `validationRequest`, then waits for Circle completion.

Success includes `action`, agent ID/name, validator, request hash/URI, transaction hash, explorer URL, `validatorNotified` and next-step guidance. Notification happens **after** on-chain success and is best-effort.

Direct-agent requests do not create a persisted job-validation inbox row. The validator needs the returned/notified hash or manual hash entry; do not promise every request appears in the job-backed inbox. There is no client idempotency key. Inspect an uncertain original transaction rather than creating another request hash.

## POST action: respond

Required fields: `action: 'respond'`, `validatorSCA`, `requestHash`, boolean `passed` and `tag`.

Before submitting, the server proves the designated validator from on-chain status. For job-backed requests it also requires the stored validator binding to agree. The submitted validator must match that identity and be controlled by the caller. A different valid wallet cannot respond.

`passed: true` maps to response 100; false maps to 0. The current transaction sends an empty response URI and a zero response-hash argument, with the supplied tag. Success includes action/hash, `passed`, `responseCode`, tag, validator, transaction hash and explorer URL. Job-backed database synchronization is best-effort after chain success; an HTTP success does not prove that synchronization completed.

## GET /api/agent/validation?requestHash={hash}

Reads `getValidationStatus` on the configured registry. Returns `success`, `requestHash`, `validation`, `validationRegistryAddress`, explorer address URL and a message.

`validation` contains `validatorAddress`, token-ID string `agentId`, numeric `response`, `passed`, `pending`, tag and update timestamps. `passed` means response exactly 100. The current `pending` flag tests whether the validator address is zero, **not whether a known designated validator has responded**. Do not treat the flag/message as a complete unknown/pending/failed lifecycle classifier.

Missing request fields/hash or invalid action returns `400`; missing agent `404`; owner/control/designated-validator mismatch `403`; caught Circle/RPC failures `500`. Consult actual receipt/status rather than assuming a timeout rolled back a write.
