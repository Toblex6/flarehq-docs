The FlareHQ API exposes invoice, wallet, identity and commerce operations. A page or endpoint existing does **not** prove that its mainnet execution is enabled or verified. Checkout is non-custodial: **the customer pays directly to the merchant wallet; FlareHQ never holds checkout funds**.

## Base URL and network

The production app origin is `https://flarehq.xyz`; endpoint paths begin at `/api/`. Network is selected by the server deployment, not an API key prefix or SDK `environment` request argument.

| Network | EVM chain ID | CCTP domain |
|---|---|---|
| Arc Mainnet | `5042` | `26` |
| Arc Testnet | `5042002` | `7` |

Mainnet uses real funds. For test development, explicitly select a testnet deployment and [Get Test Tokens](https://faucet.circle.com). Read `/api/network` for that deployment's public descriptor; it is not a payment-health guarantee.

## Authentication

Merchant API keys, active internal service keys and `merchant_token`/`consumer_token`/`admin_token` cookies are **separate** boundaries. Each route supports its own subset; some reads are public. A service key is not automatically an owning merchant or permission to debit a foreign wallet.

Use the `x-api-key` header with the issued server-side key where supported. `POST /api/keys` is admin-authorized internal service-key provisioning, not self-service merchant onboarding. See [authentication](/authentication).

For merchant `POST /api/payments/initialize`, use the merchant API key: its current resolver does not accept a bare merchant cookie. `/api/merchant/payment-link` does support the merchant cookie. Initialization also supports a consumer session or active internal key under their different semantics.

## Request and response formats

Send JSON bodies with `Content-Type: application/json`. Prefer decimal amount strings and use each endpoint's actual fields; addresses, token units and payer/recipient bindings must not be invented by an SDK example.

There is **no universal response envelope**. Initialization uses `success` and nested `data`; verification uses top-level `status` and `data.status`; configured x402 uses base64 protocol headers. An HTTP success is not proof of funds or upstream delivery.

See [errors](/developers/errors) for status interpretation and safe retry behavior. Never blindly replay a money/deployment POST after a timeout.

## Rate limits

The shared per-minute tiers are default `50`, payments `30`, agent `10`, keys `5`, escrow `20`, stream `20`, nano `100`, withdraw `5` and session `10`. They apply where a route calls the limiter, not automatically to every matching path. Upstash rejections include `Retry-After`; the process-local memory fallback may omit it.
