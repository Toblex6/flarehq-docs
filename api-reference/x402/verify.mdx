**Mainnet GatewayClient operations are disabled.** After endpoint-specific authentication, these routes return `503 gateway_mainnet_unavailable`.

## GET /api/x402/seller/balance

Use a supported API key or merchant session. On configured testnet, supply `sellerAddress` as a query parameter; if omitted, the current route falls back to the server's `SELLER_ADDRESS`. Unlike `/api/gateway`, this balance handler does not call the seller ownership gate. Do not describe it as ownership-scoped.

The response includes `sellerAddress`, `wallet` and `gateway` balance objects on a successful read. An upstream failure can instead return `success: true` with zero-filled balances and no seller address. A zero or success flag alone is not proof of a successful live balance read, a per-listing payout or a checkout merchant balance.

## POST /api/x402/seller/balance/withdraw

This route requires an API key **and caller control of the configured seller wallet** before GatewayClient construction. Its configured-testnet request uses `amount` and optional `destinationChain`/`destinationAddress`.

Destinations are restricted to the server's treasury allowlist. Without an allowlist, an explicit recipient must be the seller's own address. Supported destination chains are endpoint-defined; do not treat this as an arbitrary-address or arbitrary-chain API. Never use it as a mainnet workaround.

## No standalone verify API

There is no implemented `POST /api/x402/verify` route. Proof verification and settlement occur together at the protected resource boundary. Verifying a signature alone would not prove funds settled or that the upstream delivered.

See [x402 protocol](/x402/overview) for actual headers and [legacy seller Gateway access](./gateway.mdx) for the separately authenticated `/api/gateway` route.
