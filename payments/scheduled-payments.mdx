`POST /api/payments/scheduled` stores a recurring transfer plan. It does not pay immediately: `startImmediately` makes the first run **due now**, while a separately configured runner must execute it.

Authenticated mainnet recurring execution and the production scheduler were not verified in the November 16, 2026 readiness run. Do not treat creation as successful payment or set up a recurring debit as a smoke test. Read [availability](/payments/availability).

On November 19, web and standalone **Save** confirmation stopped at the payment-PIN dialog and was canceled without PIN entry. Standalone Save emitted zero execution POSTs. No schedule or recurring debit was created by these checks; parsed assistant wording is not execution evidence.

## Payer authorization

The caller must control `payerSCA`. Consumer create/edit/cancel retains applicable `consumer.save` step-up. The server resolves the signing wallet from the bound consumer, merchant or agent record; a body-supplied `payerWalletId` is not accepted as debit authority.

The payer must be a server-signable **Circle Developer-Controlled wallet**. EXTERNAL wallets cannot be automatically debited. An unbound Circle or retired/unknown wallet type fails closed; no missing payer inherits a shared wallet.

## Create a plan

Use supported merchant/internal-key or merchant/consumer session authentication. Keep API keys server-side; let consumer users authorize through the actual app.

```json
{
  "payerSCA": "0x...",
  "receiverSCA": "0x...",
  "amount": "0.10",
  "currency": "USDC",
  "intervalDays": 30,
  "maxRuns": 1,
  "startImmediately": false,
  "description": "Example recurring plan"
}
```

This is a shape example, not a request performed by the readiness run. Amount is a positive decimal with at most 6 decimals, capped at 10,000,000; `intervalDays` is an integer 1–3650 at creation. USDC/EURC token identity is canonical and one schedule transfers one token, not a conversion.

Omitting `maxRuns` permits indefinite recurrence. Supply a reviewed finite count; this handler's `maxRuns` parsing is not a universal strict integer guarantee. New receiver addresses can resolve to the merchant's current wallet.

## Manage and execute

- `GET /api/payments/scheduled`: own controlled-payer rows, optionally filtered by `payerSCA` and `status`.
- `PATCH`: edit an ACTIVE plan's `amount`, `intervalDays`, `description` or `maxRuns`; changing cadence recomputes the next run. Use canonical decimal/integer values; PATCH validation is not identical to strict create validation.
- `DELETE`: cancel by `reference`, with payer control and applicable step-up.
- `POST /api/payments/scheduled/run`: **internal service-key runner**, not a merchant manual-pay endpoint. It processes due rows platform-wide; do not call it as a harmless reference check.

Read the [scheduled reference](/api-reference/payments/scheduled) for exact fields and response counts. A hosted cron schedule and execution guarantees are not established merely because the source runner exists.

## Reconciliation

The runner checks the stored wallet/token, uses per-period tracked PaymentLog state, advances the schedule after confirmed transfer, and can resume an anchored Circle transaction. Top-level success is the runner response, not proof every row paid.

Inspect the actual period record, Circle ID, receipt, parties/token/amount and recipient credit. Do not replay a debit after a timeout without checking whether the tracked transfer exists. Creation-to-anchor crash and production contention behavior were not established by this docs sync.

`scheduled_payment.executed` notifications are [unsigned/best-effort](/developers/webhooks). No per-second streaming behavior is implied; current job streams use distinct criterion tranches.
