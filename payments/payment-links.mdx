Merchant payment links are shareable **single-invoice checkout references**, not permanent reusable products. `POST /api/merchant/payment-link` stores a PENDING invoice with a **24-hour expiry**. The separate initialize endpoint stores a 120-minute expiry.

**The customer pays directly to the merchant wallet; FlareHQ never holds checkout funds.** On November 19, authenticated merchant-session creation returned a 0.01-USDC link with the bound merchant recipient; public GET and read-only Neon matched its unpaid row. Hosted/embed rendering passed. One exact checkout is approved but paused for browser attachment and a different unpaid replay target; historical reconciled payments are separate from the assistant's **0-USDC** run. See [availability](/payments/availability).

## Create a link

Use a verified active merchant's API key or supported merchant session. The merchant must have a payout wallet; the server freezes that wallet and merchant identity into the invoice.

```javascript
const response = await fetch('https://flarehq.xyz/api/merchant/payment-link', {
  method: 'POST',
  headers: {
    'x-api-key': process.env.FLAREHQ_API_KEY,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ amount: '0.10', currency: 'USDC' }),
});
const link = await response.json();
if (!response.ok || link.success !== true) throw new Error('Link creation failed');
// Save link.reference; share link.checkoutUrl.
```

This is an illustrative backend request, not a performed production test. There is no `/api/payment-links` product API or `/pay/lnk_...` route in this application.

## Fields and semantics

| Field | Current behavior |
|---|---|
| `amount` | Required positive decimal, up to 6 decimals, capped at 10,000,000. Prefer a string. |
| `currency` | Accepted input but ignored by this merchant-link handler: new links always use server-resolved USDC. |
| `description` | Echoed in the response, not stored on the PaymentLog invoice by this handler. |
| `webhookUrl` | Optional stored destination; outbound deliveries are unsigned/best-effort. |

Do not send `name`, `price`, quantity, shipping-address collection, arbitrary recipient or reusable-product settings from older SDK examples. Those are not supported product features here.

The response includes `reference`, `checkoutUrl`, numeric `amount`, `currency`, canonical `token`, `description`, `merchant` and `expiresIn: '24 hours'`. It does not return a product ID, activation switch or SDK `link.url`.

## List links

`GET /api/merchant/payment-link` uses the same merchant resolver and returns that merchant's `links`. It limits the database query to the most recent 100 merchant rows, then filters for the selected network. The view includes raw and derived display statuses, `expiresAt`, token identity and checkout URL.

A row may remain raw `PENDING` after expiry while the view displays `EXPIRED`. A list response is not live receipt verification or proof that a pending payer transaction failed.

Display-only fix `4d91daf` on `final-readiness-2` gives expired links a neutral badge and separate dashboard count; Failed stays red and unknown codes do not count as Pending. Current-component/offline checks passed, including mobile navigation clearance. No invoice status or payment behavior changed, and production deployment is not claimed.

## Verify the payment

Open the actual `/checkout/{reference}` or `/checkout/embed/{reference}` URL. Before fulfillment, read `GET /api/payments/verify/{reference}`, compare the frozen invoice with your own order, and inspect receipt/recipient-credit evidence where needed. Top-level `status: true` means a successful query, not a paid order.

Do not rely on a `linkId` webhook field, shipping-address payload or signed notification: these were unsupported older examples. Use your saved reference and durable once-only fulfillment state.
