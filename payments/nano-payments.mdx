`POST /api/payments/nano` records a future debit in the NanoPayment ledger; it does **not** transfer tokens. `POST /api/payments/nano/settle` later transfers a batch from the explicitly bound payer wallet.

This is **not the settlement layer underneath Circle x402**. `withGateway()` verifies/settles its own protocol before invoking a resource. Nano ledger rows and x402 payments are separate mechanisms.

Authenticated mainnet nano settlement was not executed in the November 16, 2026 readiness run. Creating a row or showing `readyToSettle` is not payment evidence. Read [availability](/payments/availability).

## Record a charge

Use the supported merchant API key/session or active internal key. Normal callers must control **`agentSCA`, the payer**, not merely the receiving merchant. A merchant cannot charge an unrelated payer by owning `merchantSCA`. Spend limits apply before recording the future debit.

```json
{
  "agentSCA": "0x...",
  "merchantSCA": "0x...",
  "amount": "0.000100",
  "currency": "USDC",
  "description": "One service request"
}
```

This is a request shape, not a performed transaction; replace placeholders only with authorized addresses. Amount is a positive decimal with at most 6 decimals, capped at 10,000,000. Currency/address are resolved through the supported-token registry; mismatches are rejected.

Rows are grouped by **payer + merchant + canonical token**. USDC and EURC never share a settlement transfer. A historical merchant address can resolve to that merchant's current wallet; unknown addresses are not redirected.

Record success returns `nano`, `unsettledBalance`, `unsettledCount`, `currency`, `tokenAddress` and `readyToSettle`. The numeric threshold is currently **1.0 per token**. It is an eligibility hint, not an automatic background transfer.

## Read and settle

- `GET /api/payments/nano?agentSCA=...&merchantSCA=...` reads the summary under its auth wrapper. Optional `currency`/`tokenAddress` scopes one token. An unfiltered total can mix currencies: inspect `mixedTokens`/`tokenGroups`.
- Normal settlement requires the payer's registered, bound Circle wallet and payer control. Merely controlling a merchant wallet can permit recording an own-wallet charge but does not guarantee it has a registered agent wallet for settlement.
- The single-pair route normally requires the **1.0 threshold**; `forceSettle` bypasses the threshold, not ownership, token, signing or spend limits.
- The **60-second age** is used by the internal `autoSettle` eligibility path, not a promise that every single-pair request or unattended ledger entry settles on a timer.
- Platform-wide `autoSettle` requires an active internal service key. It is not a merchant automation endpoint and requires explicit production configuration.

Do not run an auto-settler against production as a documentation check. Follow the [nano reference](/api-reference/payments/nano) for actual response shapes.

## Evidence and uncertain outcomes

Inspect each token batch's Circle ID, on-chain hash, receipt, payer debit/recipient credit and matching rows. A successful top-level mixed-batch response can contain failed individual settlements. Batch PaymentLog uses `SETTLED`, distinct from checkout `SUCCESS`.

An anchored SUBMITTED transaction can resume; terminal failure and stale locks have different recovery behavior. The docs sync did not establish end-to-end crash safety or close the transfer-create-to-ID-persistence window. Reconcile before retrying, never initiate another debit because a response or notification was lost.

Outbound `nano.batch_settled` notifications are [unsigned/best-effort](/developers/webhooks), with no durable redelivery guarantee.
