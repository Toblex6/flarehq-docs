Use the authentication supported by the route you call. Some reads are public; others require a merchant API key, an active internal service key or a supported session. There is no universal credential that authorizes every API or payment operation.

## Credential types

| Credential | Boundary |
|---|---|
| Merchant API key | Issued during merchant email verification; resolves an active, verified merchant on routes that support it. |
| Internal service API key | Active `ApiKey` record; accepted only by applicable wrappers. It is not automatically a merchant identity. |
| `merchant_token` | Merchant JWT cookie; active/verified status and session version are checked by the merchant resolver. |
| `consumer_token` | Separate, database-bound consumer JWT system, also used by Telegram-linked consumers. |
| `admin_token` | Separate admin session boundary; not a merchant or consumer credential. |

Keys are issued in `arc_live_...` format. That prefix does not select mainnet/testnet or supply a scope. A separate FlareHQ publishable/secret SDK key pair is not supported.

## Obtain and protect a merchant key

Sign up and verify your merchant email. Save the API key returned once by `POST /api/merchant/verify` in a server-side secret store. Never expose it in browser JavaScript, query strings, public repositories or logs.

`POST`/`DELETE /api/keys` manage internal service keys and require administrative `x-admin-secret` authorization. They are **not self-service merchant key rotation endpoints**. Do not distribute the admin secret to an integration.

## Server-side request

```javascript
const response = await fetch('https://flarehq.xyz/api/payments/initialize', {
  method: 'POST',
  headers: {
    'x-api-key': process.env.FLAREHQ_API_KEY,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ amount: '0.10', currency: 'USDC' }),
});
```

This creates an invoice, not a payment. For merchant initialization, the payout wallet is server-resolved from the authenticated merchant.

The current `/api/payments/initialize` resolver accepts a merchant API key, active internal key or `consumer_token`; it does **not** resolve a bare `merchant_token`. The separate `/api/merchant/payment-link` route accepts the merchant key or merchant session. Follow those differences rather than assuming all merchant cookies work everywhere.

## Browser sessions and caller control

Let the application manage HTTP-only session cookies. Do not copy them into execute scripts or paste them into request headers. An API key/session passing authentication does not establish control over an arbitrary wallet.

Fund-moving and identity-sensitive operations retain endpoint-specific role and wallet ownership checks. Consumer send/save and applicable foreign-payout operations retain step-up. An own-wallet consumer **request** skips payment PIN because it only creates an invoice paying that consumer; it does not debit a wallet.

## Network and disabled features

Network selection is deployment-side. Mainnet `5042` uses real funds; testnet `5042002` uses test tokens. Do not use a request body, SDK `environment` argument or key prefix to switch chains.

Disabled features may return `503` before authentication; others authenticate first. Neither a `401` nor a successful login proves the feature is funded or enabled. See [payment availability](/payments/availability).

## Authentication failures

- `401`: missing/invalid credentials for that wrapper, or a session that no longer resolves.
- `403`: inactive service key on some wrappers, caller-control/role/step-up restrictions, or other authorization failure.
- An invalid supplied key is not guaranteed to fall back to a valid cookie.
- `429`: honor `Retry-After` if present; some fallback rate-limit responses omit it.

Coordinate revocation or replacement with the owner of that credential. Do not assume a public merchant rotation API or universal SDK error shape.
