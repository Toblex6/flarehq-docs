FlareHQ does not use one universal response envelope. Many endpoints return `success`/`error`; payment verification uses `status`/`message`/`data`; x402 challenges are protocol headers; some errors contain only `error`, `code`, `reason` or `details`. Check HTTP status **and** the route's actual body.

`HTTP 200`, `success: true` or top-level `status: true` does not by itself prove payment or upstream delivery. A verification query can succeed while `data.status` is `PENDING`. Some balance views return zero-filled values after a read failure.

## Common HTTP statuses

| Code | Interpretation and next step |
|---|---|
| `400` | Check fields, token, amount, wallet and the endpoint-specific validation message. |
| `401` | Missing or invalid supported authentication. Merchant, consumer and admin sessions are separate. |
| `402` | On configured testnet x402 resources, inspect base64 `PAYMENT-REQUIRED` and use the compatible EOA `payment-signature` protocol. Mainnet x402 is disabled. |
| `403` | Caller control, role, step-up, key status, policy or destination restriction failed. Changing an address is not an authorization fix. |
| `404` | Wrong path/reference or a record hidden from this caller. Bare `/checkout` and `/pay` are not valid invoice URLs. |
| `409` | Conflict or in-progress state. Inspect the existing attempt before creating another one. |
| `422` | A route-specific semantic check failed, such as marketplace target safety/reachability. |
| `429` | Rate limit exceeded. Respect `Retry-After` when supplied; the memory fallback can omit it. |
| `500`/`502` | Server/upstream failure; not proof that a transaction was rejected before submission. Inspect transaction state before a money retry. |
| `503` | Feature unavailable or misconfigured. Do not fund or repeatedly retry a disabled feature. |

Timeout behavior and error codes vary by route. There is no universal five-minute x402 proof rule or guarantee that every chain revert is `502`.

## Mainnet availability errors

- Escrow: `escrow_unavailable` or `escrow_misconfigured`.
- Streams: `stream_unavailable` or `stream_misconfigured`; configured legacy mutations return `STREAM_ABI_CONFIG_CONFLICT`.
- ERC-8183 jobs: `erc8183_unavailable` when the external protocol address is absent.
- x402 resources: `x402_unavailable`; Gateway buyer/balance operations use `gateway_mainnet_unavailable` at their availability gate.

Authentication can run before the availability response on some buyer routes. Mainnet x402 remains disabled even with a verifier address configured; do not bypass the gate. See [payment availability](/payments/availability).

## Rate limits

The shared limiter defines per-minute tiers: default `50`, payments `30`, agent `10`, keys `5`, escrow `20`, stream `20`, nano `100`, withdraw `5` and session `10`. These apply **where a route invokes that limiter**; path prefixes do not prove every endpoint has the same bucket.

The limiter keys on a supplied API key, otherwise a connection identity. Upstash is used when configured; its bounded memory fallback is process-local. Only the Upstash rejection path supplies `Retry-After` and rate-limit headers. Production deployment behavior was not load-tested under authenticated traffic here.

## Safe response handling

This read-only example checks the verification endpoint's real shape:

```javascript
const response = await fetch(
  `https://flarehq.xyz/api/payments/verify/${encodeURIComponent(savedReference)}`,
);
const result = await response.json();
if (!response.ok || result.status !== true) {
  throw new Error('Could not read payment status');
}
if (result.data.status !== 'SUCCESS') {
  // Keep the order unpaid; inspect expiry and any submitted transaction.
}
// Before fulfillment, compare your saved amount/currency/recipient and receipt.
```

Do not log API keys, cookies, raw signatures or private configuration. Retain the reference, safe error code, Circle transaction ID and actual transaction hash privately for reconciliation.

## Troubleshooting

<Accordion title="An invoice is PENDING or expired">
  Initialized invoices have a 120-minute expiry; merchant payment links have a 24-hour expiry. Check the stored `expiresAt` and payment status. A cached read may still say PENDING after expiry; the merchant link view exposes a derived display status. Before replacing an invoice, inspect any submitted payment so you do not collect twice.
</Accordion>

<Accordion title="A funded request timed out">
  Inspect the saved attempt, Circle status, receipt, matching database record and recipient credit. Retry only through that endpoint's documented resume/idempotency behavior. A blanket exponential retry of a POST can duplicate a payment or deployment.
</Accordion>

<Accordion title="An agent lookup returns not found">
  Verify Registry ID, ERC-8004 token ID, SCA address and network separately. Do not redeploy as the default fix: registration might already exist but await identity indexing. Use the owning merchant's deployment recovery path where applicable.
</Accordion>

<Accordion title="An outbound webhook has no signature">
  That is current behavior, not a raw-body HMAC failure. No implemented FlareHQ outbound signing secret or verified `constructEvent` helper was established. Treat it as a hint and reconcile with your saved order and verified settlement evidence.
</Accordion>
