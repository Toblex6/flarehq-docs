FlareHQ sends JSON POST notifications from selected handlers. **Outbound deliveries are unsigned, best-effort and have no durable retry queue or delivery guarantee.** There is no implemented `x-flarehq-signature` verification contract, webhook signing-secret issuance or verified `constructEvent` SDK for these messages.

An incoming POST is not proof of payment. It can be spoofed, missing or duplicated.

## Configure a destination

- Invoice/payment-link and some other create handlers accept `webhookUrl`. Follow each endpoint's actual fields rather than assuming every entity supports it.
- Merchant notification preferences use `/api/merchant/notifications/preferences`, including `webhookEnabled`, `webhookUrl` and muted events. The dispatcher only uses the preference/override URL when that merchant has enabled webhooks.
- There is no universal endpoint-registration, signing-secret or event-log replay dashboard. Do not rely on older **Settings → Webhooks → Event Log** instructions.

Review your own receiver's access controls and URL configuration. Do not place API keys in notification URLs or log credentials from an incoming request.

## Two payload families

Direct route notifications are flat objects with `event` plus route-specific fields. For example, an on-chain settlement handler sends:

```json
{
  "event": "payment.settled",
  "reference": "arc_ref_example",
  "amount": 0.1,
  "currency": "USDC",
  "status": "SUCCESS",
  "settlementType": "ONCHAIN_SCA_TRANSFER",
  "arcTxHash": "0x...",
  "circleTxId": "...",
  "explorerUrl": "https://explorer.arc.io/tx/0x..."
}
```

This is a shape example, not a transaction record. Fields vary between settlement paths. Do not require a fabricated `event.id`, `event.type`, `metadata`, recipient or timestamp common to all notifications.

Merchant preference notifications instead use the dispatcher envelope:

```json
{
  "event": "payment.received",
  "title": "...",
  "message": "...",
  "data": {},
  "sentAt": "..."
}
```

## Events found in source

These names are implementation observations, not a promise that every mainnet event can currently fire.

| Handler family | Example event names |
|---|---|
| Payment settlement | `payment.settled`, `payment.auto_settled`, `payment.detected_and_settled` |
| Nano ledger batches | `nano.batch_settled` |
| Scheduled execution | `scheduled_payment.executed` |
| Payroll | `payroll.completed` |
| Escrow routes | `escrow.created`, `escrow.released`, `escrow.disputed`, `escrow.confirmed` |
| Notification dispatcher | `payment.received`, `escrow.funded`, `escrow.incoming`, `refund.completed`, `dispute.opened`, `dispute.resolved`, `agent.budget_exceeded`, `cctp.transfer_completed`, `validation.requested` |

The retired per-second stream handlers do not emit the old create/stop/withdraw/completed lifecycle. Mainnet escrow and ERC-8183 job streams remain unavailable. Read [payment availability](/payments/availability).

## Reconcile before fulfillment

1. Parse a bounded notification body and look up the entity in **your own saved orders**. Never fetch a URL supplied by the notification.
2. Queue a reconciliation task durably. Fetch payment status from the fixed FlareHQ origin using the saved reference, not the untrusted amount or recipient.
3. Require the expected status, amount, currency, frozen recipient and actual receipt/recipient-credit evidence. The verification endpoint's top-level `status: true` means the query succeeded; payment success is `data.status === 'SUCCESS'`.
4. Fulfill once using a transactional order transition. Deduplicate by your entity/reference and verified settlement identity, not a nonexistent universal webhook event ID.
5. Reconcile pending orders independently of notifications. HTTP success or a webhook failure does not determine whether money moved.

`GET /api/payments/verify/{reference}` reads cached database state; it does not itself re-read or settle the chain. Use owner-authorized records and the actual receipt when stronger settlement proof is needed.

## Delivery and retries

Some handlers await their notification fetch; others fire it without waiting. Neither implementation has a durable retry schedule, stored delivery-attempt log or manual replay API. A non-2xx receiver response is not guaranteed to produce a retry.

Only acknowledge after your own reconciliation task is durably accepted. Do not depend on a promised one/five/thirty-minute redelivery schedule, and do not retry a fund-moving operation just because its notification did not arrive.

## Inbound platform webhooks are different

`POST /api/webhooks/circle` verifies Circle's signed inbound webhook, and `POST /api/telegram/webhook` uses Telegram's configured secret-token boundary. Those controls do **not** sign FlareHQ's outbound notifications to your server.
