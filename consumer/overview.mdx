Consumer accounts use the `consumer_token` session, separate from merchant/admin authentication. You can sign in through verified email or prove control of an existing wallet. **A bare wallet address is not a login credential.**

## Sign in or create an account

- **Email:** `POST /api/consumer/email-auth` requests a code; `PUT` with email/code resolves the account or provisions a Circle wallet for a new verified email. A returning external account is not automatically converted into a Circle wallet.
- **Existing wallet:** request a nonce challenge with `GET /api/consumer/session?nonce=1&address={address}`, sign the returned message in your wallet, then POST `walletAddress`, `message` and `signature` while retaining the nonce cookie.
- **Legacy empty session POST:** can provision a new Circle wallet for callers without a resolvable EXTERNAL session. An EXTERNAL session receives `403 EMAIL_VERIFICATION_REQUIRED`; use email onboarding rather than repeatedly creating wallets. An empty POST is not an existing-account recovery flow.

The session lasts 30 days and is bound to the database account/session version. [The session reference](/api-reference/consumer/session) explains liveness errors and logout. FlareHQ does not see external-wallet private keys; Circle Developer-Controlled wallets use server-authorized signing. Do not describe every operation as external self-signing.

## Balance and activity

[GET /api/consumer/balance](/api-reference/consumer/balance) reads the configured network's canonical token balance. It defaults to USDC; EURC/CIRBTC depend on network support. Balance output is not a fixed six-place accounting string or fixed-block reconciliation proof.

[GET /api/consumer/activity](/api-reference/consumer/activity) merges a recent stored-payment sample with EXECUTED swaps and COMPLETED external bridge intents. It is not an exhaustive wallet transaction scan. Pending requests, row timestamps and display direction do not independently establish payment.

## Send or request

[POST /api/payments/initialize](/api-reference/payments/initialize) creates an invoice under consumer send/request semantics. Mainnet invoice creation is USDC-only; the customer pays directly to the frozen recipient wallet. Creation is not a transfer.

On the readiness branch, an own-wallet consumer `request` skips payment PIN when `payoutAddress` is omitted or equals the signed-in wallet. Sending, saving and foreign-payout requests retain their applicable step-up. The assistant compares an explicit payout with the authenticated wallet instead of silently dropping the destination.

Authenticated web and Telegram request tests are still owner-dependent. Telegram workers use the same ConsumerAccount/session boundary; wallet setup is not a separate Telegram authority.

## Bridge, swap and unavailable features

Circle bridge and external-wallet bridge are different paths. The Circle path does **not** provision a source-chain wallet and rejects a non-Arc source for this account. External bridging requires supported source funds/gas and a server-resolved linked destination. See [CCTP](/payments/cctp-bridge).

Separate Flow swaps have offline mainnet warning/block evidence, but no funded production round-trip was performed. Mainnet x402, unconfigured ERC-8183 actions and job streams are unavailable on the review branch. Do not fund an SCA or EOA based on a promised automatic job payout or per-second salary.

Read [mainnet availability](/payments/availability) and verify the actual network, wallet binding, recipient and evidence before authorizing funds.
