## Mainnet status — November 16, 2026

**ERC-8183-dependent job actions are unavailable on mainnet.** No verified mainnet protocol address was found in the readiness run. The server resolves `ARC_MAINNET_ERC8183_ADDRESS` through network configuration and refuses with `503 erc8183_unavailable` when absent; authentication or validation may run first on individual routes.

An ERC-8004 identity, marketplace listing or stream deployment does not supply this dependency. Do not copy the testnet pin into mainnet configuration or deploy a substitute external protocol.

Read-only lists and pre-chain postings can remain visible. Visibility does not mean a job was accepted, funded, submitted or completed on-chain. The readiness branch disables unavailable protocol actions using the server-resolved network descriptor.

## Configured testnet lifecycle

The roles are distinct: the client hires/funds, the provider submits work and the evaluator approves completion. Use the endpoint-specific authenticated wallet and caller-control checks; consumer job funding also retains step-up.

| Stage | Actual route family |
|---|---|
| Hire a validated provider | `/api/agents/{reference}/hire` or the registry/procurement workflow |
| Low-level protocol create | `/api/jobs/create` |
| Set budget | `/api/jobs/set-budget` |
| Fund | `/api/jobs/fund` or the applicable job-specific funding route |
| Submit work | `/api/jobs/submit` |
| Complete | `/api/jobs/complete` |

Follow the returned `jobId`, `nextSteps`, wallet bindings and budget units. Registry ID, ERC-8004 token ID, Circle wallet ID and job ID are not interchangeable. A create response is not proof of funding or completion.

Current `POST /api/jobs` Direct Hire validates known provider serviceability, writes a canonical ERC-8183 job row best-effort and notifies linked Telegram human providers best-effort. It still has different inputs/policy machinery from registry/procurement and no registered agent-owner job-hire notification event. Older blanket claims of no provider validation are stale; none of these source facts proves a funded mainnet job.

## Criterion-based job streams

`/api/jobs/nanopay/open`, `/release` and `/close` implement acceptance-criterion tranches, **not per-second accrual**. Opening requires a **FUNDED ERC-8183 job**, non-empty criteria and a configured stream contract. It approves and locks the job budget from the authorized poster; do not assume it merely changes a label on an existing escrow.

Closing pays the remaining stream budget to the **worker**, not a poster refund. Read [streaming availability](/payments/streaming-payments). No mainnet open/release/close transaction was executed here.

## Verification

Before claiming any funded lifecycle, reconcile the relevant receipt, actual parties and amount, matching job/stream database records, and explorer evidence. An HTTP success, animation or local test is insufficient.
