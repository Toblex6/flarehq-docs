## Mainnet status — November 19, 2026

**FlareHQ x402 execution is disabled on mainnet**, even if a verifier address is configured. Resource routes return `503 x402_unavailable` before creating a payment challenge. Buyer wallet, pay, deposit and seller GatewayClient routes return `503 gateway_mainnet_unavailable`, subject to their own authentication wrappers.

Circle publishes Arc mainnet Gateway support and a GatewayWallet verifier. That does not prove FlareHQ's complete challenge, authorization, verify/settle and withdrawal integration works. No configuration was changed and no mainnet x402 payment was executed in this readiness run.

November 19 Brain and nano checks reached the mainnet unavailable responses without a paid execution. The disablement remains intentional; verifier bytecode alone is not integration evidence or permission to enable x402.

## Configured testnet behavior

The existing `withGateway()` integration uses x402 version 2 and Circle batching:

1. A request without a payment signature receives `402` with a **base64 JSON `PAYMENT-REQUIRED` header**. The response body is `{}`.
2. The decoded header contains `x402Version`, `resource` and `accepts`. Each accepted requirement binds `scheme`, `network`, `asset`, `amount`, `payTo`, `maxTimeoutSeconds` and `extra`.
3. The payer supplies a compatible authorization in a **base64 JSON `payment-signature` header**. Payers must be **EOAs, not Circle SCAs**.
4. The facilitator verifies and settles **before the handler runs**. A later upstream failure does not undo payment.
5. A successful handler response includes a base64 `PAYMENT-RESPONSE` header. Its `transaction` may be a Gateway reference, not a mined transaction hash.

Do not invent a separate proof header or use a `{ price, chainId }` body as this integration's challenge. Read the returned requirement rather than hardcoding the asset, verifier or recipient. The ERC-8004 identity registry is **not** a payment recipient.

## Separate products

- [`POST /api/x402/pay`](/api-reference/x402/pay) is an authenticated buyer convenience route using a merchant-bound EOA. It accepts `resourceUrl` and optional `body`; it does not accept a marketplace slug plus client payment proof.
- [Marketplace discovery](/x402/marketplace) and listing administration are not evidence of paid execution. Agent listings use hiring, not per-request payment.
- Structured agent-to-agent transfers are direct on-chain payments, not Circle Gateway settlement.
- The legacy demo `/api/protected-service` uses separate Gateway Rails behavior; it is not `withGateway()`.

Read [paywall setup](/x402/paywall-setup) before testing and [seller Gateway access](/api-reference/x402/gateway) before treating balances or references as spendable funds.
